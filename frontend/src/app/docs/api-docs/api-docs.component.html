実効手数料率は、トランザクション自体に設定された手数料率と常に同じではありません。例えば、表示された範囲が5〜72 sat/vBのブロックに1 sat/vBのトランザクションがある場合、高い手数料率の子トランザクションによって実効手数料率が5 sat/vB以上に引き上げられた可能性があります（これがCPFPによる手数料引き上げです）。この場合、1 sat/vBを範囲の下限とすると、実際に承認に必要だった手数料を正しく表せません。

各トランザクションの手数料率は詳細ページで確認できます。CPFPの関係がある場合は、実効手数料率と子孫・祖先トランザクションへのリンクも表示されます。

Mempool 旨在显示区块的有效手续费率范围，即让交易被包含在区块中实际需要支付的费率。

交易的有效费率不一定等于其明确设置的费率。例如，在显示 5–72 sat/vB 范围的区块中看到一笔 1 sat/vB 的交易时，它可能有一笔高费率的子交易，将其有效费率提高到 5 sat/vB 或以上（这就是 CPFP 加速）。在这种情况下，以 1 sat/vB 作为区块费率范围下限会产生误导，因为确认该交易实际需要更高的费率。

交易详情页显示交易的手续费率。如果有 CPFP 关系，页面还会显示有效手续费率及后代和／或祖先交易的链接。

Mempool, bir işleme blokta yer verilmesi için gerçekte ne kadar ödeme gerektiğini ifade eden etkin ücret oranı aralığını göstermeyi amaçlar.

Bir işlemin etkin oranı, açıkça belirlenen oranla her zaman aynı değildir. Örneğin gösterilen aralığı 5–72 sat/vB olan bir blokta 1 sat/vB'lik işlem görürseniz, yüksek oranlı bir alt işlem onun etkin oranını 5 sat/vB veya üstüne çıkarmış olabilir (CPFP ile ücret artırma böyle çalışır). Bu durumda, işlemin o blokta onaylanması aslında daha fazlasını gerektirdiği için 1 sat/vB'yi aralığın alt sınırı olarak kullanmak yanıltıcı olur.

İşlem ücret oranını ayrıntı sayfasında görebilirsiniz. CPFP ilişkileri varsa sayfa ayrıca etkin oranı ve alt ve/veya üst işlemlerin bağlantılarını gösterir.

Mempool probeert het bereik van het effectieve tarief voor blokken te tonen: hoeveel je daadwerkelijk moest betalen om een transactie in een blok opgenomen te krijgen.

Het effectieve tarief is niet altijd gelijk aan het expliciet ingestelde tarief. Zie je bijvoorbeeld een transactie van 1 sat/vB in een blok met een bereik van 5–72 sat/vB, dan kan een kindtransactie met een hoog tarief haar effectieve tarief tot 5 sat/vB of hoger hebben verhoogd. Zo werkt CPFP. In dat geval zou 1 sat/vB als ondergrens misleidend zijn omdat voor bevestiging in dat blok feitelijk meer nodig was.

Het tarief staat op de transactiepagina. Bij CPFP-relaties toont die pagina ook het effectieve tarief en links naar afstammende en/of vooroudertransacties.

Mempool aims to show you the effective feerate range for blocks—how much would you actually need to pay to get a transaction included in a block.

A transaction's effective feerate is not always the same as the feerate explicitly set for it. For example, if you see a 1 s/vb transaction in a block with a displayed feerate range of 5 s/vb to 72 s/vb, chances are that 1 s/vb transaction had a high-feerate child transaction that boosted its effective feerate to 5 s/vb or higher (this is how CPFP fee-bumping works). In such a case, it would be misleading to use 1 s/vb as the lower bound of the block's feerate range since it actually required more than 1 s/vb to confirm that transaction in that block.

You can find a transaction's feerate on its transaction details page. If the transaction has any CPFP relationships, the page will also show the transaction's effective feerate along with links to descendent and/or ancestor transactions.

Una auditoría compara visualmente el bloque esperado por Mempool con el bloque real de una altura determinada.

Mempool observa su propio mempool y ejecuta una implementación del algoritmo de selección de transacciones de Bitcoin Core para determinar las transacciones que espera en próximos bloques (código fuente). Como llegan transacciones continuamente, el algoritmo se ejecuta cada dos segundos y los bloques previstos cambian casi en tiempo real.

Cuando se mina un bloque, Mempool guarda una instantánea de la plantilla prevista. Esta instantánea se llama bloque esperado para esa altura y sirve de base para la auditoría.

Cuando ambos bloques están disponibles se comparan. La auditoría intenta deducir si los mineros incluyeron o excluyeron transacciones deliberadamente. Como no puede saberse con certeza, se usan heurísticas.

  • Añadida: aparece en el bloque real pero no en el esperado y está muy fuera del rango de comisiones esperado o no estaba en el mempool. Podría haberse priorizado o recibido fuera de banda. No reduce la salud del bloque.
  • Difundida recientemente: estaba en el bloque esperado pero no en el real y el nodo la observó menos de tres minutos antes de minar el bloque. La latencia puede impedir que llegue al minero, por lo que no se considera una exclusión intencional ni reduce la salud.
  • Comisión marginal: está en el extremo inferior del rango esperado y falta en uno de los bloques. Otra transacción podría haberla desplazado; no se considera una diferencia destacable ni reduce la salud.
  • Eliminada: estaba en el bloque esperado pero no en el real, no es reciente ni de comisión marginal. Pudo haberse excluido deliberadamente y reduce la salud del bloque.

  • Retirée : présente dans le bloc attendu mais pas dans le bloc réel, sans être récente ni à frais marginaux. Elle a pu être exclue délibérément et réduit la santé du bloc.

Ein Block-Audit vergleicht den von Mempool erwarteten Block visuell mit dem tatsächlichen Block einer bestimmten Höhe.

Mempool beobachtet seinen eigenen Mempool und führt eine Neuimplementierung des Transaktionsauswahlalgorithmus von Bitcoin Core aus, um die für kommende Blöcke erwarteten Transaktionen zu bestimmen (Quellcode). Da ständig neue Transaktionen eintreffen, läuft der Algorithmus alle zwei Sekunden; die für kommende Blöcke prognostizierten Transaktionen ändern sich daher nahezu in Echtzeit.

Beim Mining eines neuen Blocks speichert Mempool eine Momentaufnahme der prognostizierten Vorlage. Dieser erwartete Block für die betreffende Höhe bildet die Grundlage des Audits.

Wenn erwarteter und tatsächlicher Block vorliegen, werden sie verglichen. Block-Audits versuchen abzuleiten, ob Miner Transaktionen absichtlich aufgenommen oder ausgeschlossen haben. Da sich das nicht sicher wissen lässt, verwendet Mempool Heuristiken:

  • Hinzugefügt: Eine Transaktion fehlt im erwarteten, steht aber im tatsächlichen Block und liegt entweder weit außerhalb des erwarteten Gebührenbereichs oder war gar nicht im Mempool. Der Miner könnte sie priorisiert oder außerhalb des Netzwerks erhalten haben. Sie verschlechtert die Blockgesundheit nicht.
  • Kürzlich verbreitet: Sie stand im erwarteten, aber nicht im tatsächlichen Block und wurde vom Knoten weniger als drei Minuten vor dem Mining gesehen. Wegen Netzwerklatenz kann der Miner sie möglicherweise noch nicht erhalten haben; ein absichtlicher Ausschluss wird nicht angenommen. Sie verschlechtert die Blockgesundheit nicht.
  • Grenzgebühr: Sie liegt am unteren Ende des erwarteten Gebührenbereichs und fehlt in einem der beiden Blöcke. Eine andere Transaktion könnte sie verdrängt haben; die Abweichung gilt nicht als bemerkenswert und verschlechtert die Blockgesundheit nicht.
  • Entfernt: Sie stand im erwarteten, aber nicht im tatsächlichen Block und gilt weder als kürzlich verbreitet noch als Grenzgebühr. Sie könnte absichtlich ausgeschlossen worden sein und verschlechtert die Blockgesundheit.

Аудит визуально сравнивает ожидаемый Mempool блок с фактическим на определённой высоте.

Mempool наблюдает свой мемпул и использует повторную реализацию алгоритма выбора транзакций Bitcoin Core для прогноза следующих блоков (исходный код). Алгоритм запускается каждые 2 секунды, поэтому прогнозируемые блоки меняются почти в реальном времени.

При добыче блока Mempool сохраняет снимок прогнозируемого шаблона следующего блока. Этот ожидаемый блок для соответствующей высоты служит основой аудита.

Когда сведения об ожидаемом и фактическом блоках доступны, их можно сравнить. Цель аудита — предположить, какие транзакции майнер мог намеренно включить или исключить. Это нельзя определить точно, поэтому Mempool использует эвристики.

Цвета обозначают различные случаи:

  • ■Добавлено

    Синим показана транзакция, отсутствующая в ожидаемом блоке, но присутствующая в фактическом, если её ставка сильно отличается от ожидаемого диапазона или она вообще отсутствовала в мемпуле. Майнер мог намеренно повысить её приоритет или получить её вне публичного распространения.

    Такие транзакции не ухудшают состояние блока.

  • ■Недавно передано

    Тёмно-розовым показана транзакция, которая была в ожидаемом, но отсутствует в фактическом блоке и впервые замечена узлом Mempool менее чем за 3 минуты до добычи. Из-за задержек сети майнер мог не успеть её получить, поэтому она не считается намеренно исключённой и не ухудшает состояние блока.

  • ■Пограничная комиссия

    Затемняется транзакция с нижнего края ожидаемого диапазона комиссий, отсутствующая в ожидаемом или фактическом блоке. Её могла вытеснить добавленная транзакция либо другая транзакция с похожей низкой ставкой. Отклонение не считается существенным и не ухудшает состояние блока.

  • ■Удалено

    Ярко-розовым показана транзакция, присутствовавшая в ожидаемом, но отсутствующая в фактическом блоке, если она не является недавно переданной или пограничной по комиссии. Она достаточно долго находилась в мемпуле для распространения, а её ставка уверенно попадает в ожидаемый диапазон. Возможно, майнер исключил её намеренно; такие транзакции ухудшают состояние блока.

ブロック監査は、あるブロック高におけるMempoolの予想ブロックと実際のブロックを視覚的に比較します。

予想ブロックを作るため、Mempoolは観測したメンプールを監視し、Bitcoin Coreのトランザクション選択アルゴリズムを再実装して今後のブロックに含まれると予想されるトランザクションを求めます（ソースコード）。新しいトランザクションが絶えず流入するため、このアルゴリズムは2秒ごとに実行され、予測ブロックもほぼリアルタイムに変化します。

新しいブロックが採掘された瞬間に、次のブロックの予測テンプレートのスナップショットを保存します。これを対象のブロック高の予想ブロックと呼び、監査の基礎とします。

予想ブロックと実際のブロックの詳細がある場合、両者を比較できます。監査の目的は、マイナーがトランザクションを意図的に追加または除外した可能性を推測することです。正確に知ることはできないため、いくつかの推定ルールを使用します。

監査では、これらの推定結果を色で表示します。

  • ■Added

    予想ブロックになく実際のブロックにあり、予想手数料率の範囲から大きく外れている、またはメンプールに存在しなかったトランザクションを青で表示します。マイナーが意図的に優先したか、別経路で受け取った可能性があります。追加分はブロックヘルスを下げません。

  • ■Recently broadcasted

    予想ブロックにあり実際のブロックにはなく、採掘前3分以内にMempoolのBitcoinノードが初めて観測したものを濃いピンクで表示します。ネットワーク遅延などでマイナーのノードにまだ届いていなかった可能性があるため、意図的な除外とはみなさず、ブロックヘルスも下げません。

  • ■Marginal fee

    予想手数料率の下限付近にあり、予想または実際のブロックの一方にないものを暗く表示します。追加されたものや、同じく範囲の下限付近にあった別のトランザクションに押し出された可能性があり、注目すべき差とはみなさず、ブロックヘルスも下げません。

  • ■Removed

    予想ブロックにあり実際のブロックにはなく、最近の送信にも境界付近の手数料にも該当しないものを明るいピンクで表示します。十分に伝播する時間があり、予想範囲内の手数料率を持つため、意図的に除外された可能性があります。この分類はブロックヘルスを下げます。

区块审计将 Mempool 对特定区块高度的预期区块与实际区块进行可视化比较。

为了确定预期区块，Mempool 监控自己看到的内存池，并重新实现 Bitcoin Core 的交易选择算法，计算预计会进入未来区块的交易（源代码）。由于新交易不断流入，该算法每 2 秒运行一次，因此未来预测区块几乎实时变化。

新区块挖出时，Mempool 会保存下一区块预测模板的快照，称为对应区块高度的预期区块，并以此作为审计基础。

当预期区块和实际区块的详情均可用时，就可以进行比较。区块审计的目的是推测矿工何时有意纳入或排除交易。由于无法准确得知其意图，Mempool 使用若干启发式规则。

  • ■Added

A block audit visually compares Mempool's expected block to the actual block for a particular block height.

How is the expected block determined? Mempool monitors its view of the mempool and runs a re-implementation of Bitcoin Core's transaction selection algorithm to determine the transactions it expects to see in upcoming blocks (source code here). Since there is a continual flow of new transactions, this algorithm runs every 2 seconds, and as a result, you will see the transactions projected to be in upcoming blocks change in near real-time.

At the moment a new block is mined, Mempool saves a snapshot of its projected block template for the next block. We call this snapshot the expected block for the block height in question, and it serves as the basis for the block audit.

When details for an expected block and actual block are available, we can compare them. The purpose of block audits is to deduce when miners intentionally include or exclude transactions from blocks they mine. Since this information cannot be precisely known, Mempool uses a handful of heuristics to accomplish this.

Block audits highlight transactions in different colors to convey these heuristics:

  • ■Added

    A transaction is highlighted blue if it is not present in the expected block, present in the actual block, and also either:

    • far out of the expected feerate range, meaning the miner may have intentionally prioritized the transaction
    • not in the mempool at all, meaning the miner may have accepted the transaction out-of-band

    Added transactions do not negatively affect block health.

  • ■Recently broadcasted

    A transaction is highlighted dark pink if it is present in the expected block, not present in the actual block, and was first seen by Mempool's Bitcoin node within 3 minutes of the block being mined.

    Due to network latency and other factors, it can take time for a miner's Bitcoin nodes to receive a transaction, so we do not assume a miner has intentionally excluded such a transaction from a block.

    Recently-broadcasted transactions do not negatively affect block health.

  • ■Marginal fee

    A transaction is darkened if it is in the low end of the expected feerate range and missing in either the expected block or the actual block.

    Such a transaction may have been displaced by an added transaction, or it may have been displaced by another transaction from the mempool that was also at the low end of the expected feerate range for the block. In either case, the deviation is not considered notable.

    Marginal fee transactions do not negatively affect block health.

  • ■Removed

    A transaction is highlighted bright pink if it is present in the expected block, not present in the actual block, and qualifies as neither recently-broadcasted nor marginal-fee. In other words, it has been in the mempool long enough to be widely propagated and has a feerate that is well within the range expected for the block. There is a chance such a transaction may have been intentionally excluded from the block.

    Removed transactions do negatively affect block health.

Block health is a measure of how many transactions appear to be intentionally excluded from a block—a block without any transactions that appear intentionally excluded will have 100% health, while a block with 1 or more transactions that appear intentionally excluded will have sub-100% health.

How is it calculated? Let sexpected be the set of all transactions in Mempool's expected block and let sactual be the set of all transactions in the actual block. Then let n be the number of all transactions in both sexpected and sactual.

Furthermore, let r be the number of transactions Mempool deduces were intentionally excluded from sactual.

Block health is calculated as n / ( n + r ).

The number of transactions appearing in both sexpected and sactual is used (instead of a block's full transaction count) in order to minimize chances that block health is inadvertently impacted by transactions that were most likely not intentionally excluded:

  • recently-broadcast transactions, since the miner may simply not have received them
  • certain low-feerate transactions, since the miner may have opted to replace them with more profitable out-of-band transactions

As a result, block health is not intended to be a measure of how closely an expected block resembles an actual block. The actual block can be vastly different from the expected block, but if no transactions appear to be intentionally excluded, it will have a high health rating (extreme example).

Essas restrições podem, por vezes, levar à inclusão de transações com taxas por byte virtual inferiores antes de outras com taxas mais elevadas.

Por exemplo, se restar muito pouco espaço num bloco previsto, pode caber mais uma transação pequena com taxa por byte virtual baixa, enquanto transações maiores com taxa por byte virtual superior têm de esperar pelo bloco seguinte.

Um efeito semelhante pode ocorrer quando há muitas transações com muitas sigops. Cada bloco previsto só pode incluir transações até ao limite de 80 000 sigops; o espaço restante só pode ser preenchido por transações sem sigops, potencialmente com taxas por byte virtual muito inferiores.

Em casos extremos, isso pode produzir vários blocos previstos consecutivos com intervalos de taxas por byte virtual sobrepostos, pois cada bloco contém transações com taxa por byte virtual elevada e muitas sigops e transações de taxa inferior sem sigops.

The projected mempool blocks represent what we expect the next blocks would look like if they were mined right now, and so each projected block follows all of the same rules and constraints as real mined blocks.

Those constraints can sometimes cause transactions with lower fee rates to be included "ahead" of transactions with higher rates.

For example, if one projected block has a very small amount of space left, it might be able to fit one more tiny low fee rate transaction, while larger higher fee rate transactions have to wait for the following block.

A similar effect can occur when there are a large number of transactions with very many sigops. In that scenario, each projected block can only include up to 80,000 sigops worth of transactions, after which the remaining space can only be filled by potentially much lower fee transactions with zero sigops.

In extreme cases this can produce several projected blocks in a row with overlapping fee ranges, as a result of each projected block containing both high-feerate high-sigop transactions and lower feerate zero-sigop transactions.

  3. mempool/electrs, usato da mempool.space, può essere adatto a hardware più potente. Deriva da Esplora di Blockstream, a sua volta derivato da romanz/electrs, ed è pensato per installazioni più grandi.

Se ocorrerem erros ao consultar endereços, a causa pode ser o servidor Electrum utilizado como backend.

O Mempool utiliza um servidor Electrum para estas consultas. Existem várias implementações do protocolo e a escolha afeta o desempenho:

  1. romanz/electrs é uma escolha comum pelos seus baixos requisitos. Funciona bem para consultas básicas, mas consultas mais exigentes, como endereços com muitas transações, podem ser lentas, sobretudo em dispositivos de baixa potência como o Raspberry Pi.
  2. Fulcrum requer mais recursos, mas pode funcionar num Raspberry Pi e processa consultas exigentes com maior eficiência.
  3. mempool/electrs, utilizado pelo mempool.space, pode ser adequado a hardware mais potente. É uma bifurcação do Esplora da Blockstream, por sua vez derivado do romanz/electrs, e destina-se a instalações maiores.

Ошибки при поиске адресов могут быть связаны с сервером Electrum.

Mempool использует сервер Electrum для поиска адресов. Поддерживаются разные реализации протокола; выбранная реализация влияет на производительность:

  1. romanz/electrs — популярный вариант с низкими требованиями к ресурсам, используемый в большинстве дистрибутивов полных узлов. Он хорошо работает с простыми запросами, но может испытывать трудности с адресами, содержащими множество транзакций, особенно на маломощном оборудовании вроде Raspberry Pi.
  2. Fulcrum требует больше ресурсов, но может работать на Raspberry Pi и эффективнее обрабатывает сложные запросы. Если у вас проблемы с romanz/electrs, попробуйте Fulcrum.
  3. mempool/electrs подходит для более мощного оборудования. Этот сервер используется mempool.space и является форком Esplora от Blockstream, которая основана на romanz/electrs. Он предназначен для высокой производительности и крупных развёртываний.

アドレス検索でエラーが発生する場合は、バックエンドのElectrumサーバーが原因の可能性があります。

Mempoolはアドレス検索にElectrumサーバーを使用します。Electrumサーバープロトコルには複数の実装があり、どれを使用するかによって性能が変わります。

  1. romanz/electrsは必要なリソースが少なく、多くのフルノード配布版で使用されています。基本的な検索には適していますが、トランザクション数の多いアドレスなどの負荷の高い検索では、特にRaspberry Piのような低消費電力のハードウェアで遅くなる場合があります。
  2. Fulcrumはromanz/electrsより多くのリソースを必要としますが、Raspberry Piでも動作し、負荷の高い検索をより効率的に処理します。romanz/electrsで問題がある場合は試す価値があります。
  3. mempool/electrsは、より高性能なハードウェア向けの選択肢で、mempool.spaceのバックエンドとして使われています。romanz/electrsを基にしたBlockstreamのEsploraから派生し、高い性能と大規模な運用を目的としています。

如果查询地址时出现错误，可能是 Electrum 服务器后端导致的。

Mempool 使用 Electrum 服务器查询地址。Electrum 服务器协议有多种实现，Mempool 均可使用，但所选实现会影响性能：

  1. romanz/electrs 对资源要求较低，许多全节点发行版使用它。它适合基本查询，但查询交易数量很多的地址等较重请求时可能吃力，尤其是在 Raspberry Pi 等低功耗硬件上。
  2. Fulcrum 比 romanz/electrs 需要更多资源，但仍可在 Raspberry Pi 上运行，处理复杂查询也更高效。如果使用 romanz/electrs 遇到问题，可以尝试 Fulcrum。
  3. mempool/electrs 是 mempool.space 使用的后端，适合更强大的硬件。它派生自 Blockstream 的 Esplora，而 Esplora 又派生自 romanz/electrs，旨在提供高性能和支持大规模部署。

Adres sorgularında hata alıyorsanız bunun nedeni Electrum sunucu arka ucunuz olabilir.

Mempool adres sorguları için bir Electrum sunucusu kullanır. Electrum sunucu protokolünün birden çok uygulaması vardır ve Mempool bunları kullanabilir; ancak seçim performansı etkiler:

  1. romanz/electrs, düşük kaynak gereksinimleri nedeniyle yaygın bir seçimdir ve çoğu tam düğüm dağıtımı bunu kullanır. Temel sorgularda iyi çalışır ancak çok işlemli adresleri sorgulamak gibi ağır isteklerde, özellikle Raspberry Pi gibi düşük güçlü donanımlarda zorlanabilir.
  2. Fulcrum, romanz/electrs'ten daha çok kaynak gerektirir ancak Raspberry Pi üzerinde de çalışabilir ve ağır sorguları daha verimli işler. romanz/electrs ile sorun yaşıyorsanız denenebilir.
  3. mempool/electrs, daha güçlü donanımlar için bir seçenektir ve mempool.space'in arka ucudur. Blockstream'in Esplora'sından çatallanmıştır; Esplora da romanz/electrs'ten türemiştir. Yüksek performans ve büyük ölçekli kurulumlar için tasarlanmıştır.

Fouten bij het opzoeken van adressen kunnen worden veroorzaakt door je Electrum-serverbackend.

Mempool gebruikt een Electrum-server voor adresopzoekingen. Er zijn verschillende implementaties van het protocol en Mempool kan ze gebruiken, maar de keuze beïnvloedt de prestaties:

  1. romanz/electrs wordt vaak gekozen vanwege de lage resource-eisen en wordt door veel full-node-distributies gebruikt. Het werkt goed voor eenvoudige zoekopdrachten, maar zware zoekopdrachten zoals adressen met veel transacties kunnen lastig zijn, vooral op lichte hardware zoals een Raspberry Pi.
  2. Fulcrum vereist meer resources dan romanz/electrs, maar kan op een Raspberry Pi draaien en verwerkt zware zoekopdrachten efficiënter. Bij problemen met romanz/electrs kan Fulcrum het proberen waard zijn.
  3. mempool/electrs is de backend van mempool.space en een optie voor krachtigere hardware. Het is een fork van Blockstream Esplora, dat weer van romanz/electrs afstamt, en is bedoeld voor hoge prestaties en grotere implementaties.

주소 조회 중 오류가 발생한다면 Electrum 서버 백엔드가 원인일 수 있습니다.

Mempool은 주소 조회에 Electrum 서버를 사용합니다. Electrum 서버 프로토콜에는 여러 구현이 있고 Mempool은 이들을 사용할 수 있지만, 선택한 구현이 성능에 영향을 줍니다.

  1. romanz/electrs: 필요한 자원이 적어 흔히 선택되며 대부분의 풀 노드 배포판이 사용합니다. 기본적인 조회는 잘 처리하지만 거래가 많은 주소 조회처럼 부하가 큰 요청은 특히 Raspberry Pi 같은 저전력 기기에서 어려울 수 있습니다.
  2. Fulcrum: romanz/electrs보다 자원이 더 필요하지만 Raspberry Pi에서도 실행할 수 있으며 무거운 요청을 훨씬 효율적으로 처리합니다. romanz/electrs에 문제가 있다면 시도해 볼 만합니다.
  3. mempool/electrs: 성능이 높은 하드웨어가 있다면 mempool.space에서 사용하는 이 백엔드를 고려할 수 있습니다. romanz/electrs에서 파생된 Blockstream Esplora의 포크이며 최대 성능과 대규모 배포를 목표로 합니다.

If you're getting errors when doing address lookups, it's probably because of your Electrum server backend.

Mempool uses an Electrum server to do address lookups. There are several implementations of the Electrum server protocol, and Mempool can use any of them, but the implementation you use affects performance:

  1. romanz/electrs. This is a common choice for its low resource requirements, and most full-node distros use it. But while this implementation works great for basic queries, it will struggle with heavier ones (e.g. looking up addresses with many transactions)—especially when running on low-power hardware like a Raspberry Pi.
  2. Fulcrum. Fulcrum requires more resources than romanz/electrs but it can still run on a Raspberry Pi, and it handles heavy queries much more efficiently. If you're having issues with romanz/electrs, Fulcrum is worth a try.
  3. mempool/electrs. If you have stronger hardware, you could consider running mempool/electrs, the backend that powers mempool.space. It's a fork of Blockstream's Esplora, which is in turn a fork of romanz/electrs, intended for maximum performance and larger-scale deployments.
